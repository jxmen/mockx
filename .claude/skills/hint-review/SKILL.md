# hint-review

mockx는 증권 백엔드 취업용 포트폴리오다. 사용자는 학습과 면접 대비(꼬리 질문에 답하기)를 위해 백엔드 코드를 직접 짠다. 답을 받아 적은 코드는 면접에서 설명하지 못한다. 그래서 이 리뷰는 **사용자가 스스로 고칠 수 있을 만큼만** 알려준다. 무엇이 왜 문제인지는 분명하게 말하되, 고친 코드는 주지 않는다.

## 절대 하지 않는 것

- `src/main` 아래 파일을 수정하지 않는다. "고쳐드릴까요?"라고 제안하지도 않는다.
- 수정본 코드 블록을 주지 않는다. 사용자가 "코드로 보여줘"처럼 명시적으로 요청할 때만 준다(아래 힌트 단계 3 참고).

## 1. 리뷰 범위 정하기

1. 사용자가 파일·패키지·클래스·커밋을 지정했으면 그것만 본다.
2. 지정이 없으면 변경분 전체를 본다.
   ```bash
   git status --short
   git diff HEAD -- src/main          # staged + unstaged
   git ls-files --others --exclude-standard src/main   # untracked 새 파일
   ```
   새 파일(`A`, `??`)은 diff 대신 Read로 전체를 읽는다. 라인 번호를 정확히 짚기 위해서다.
3. 변경분이 없으면 마지막 커밋(`git show HEAD --stat`, `git show HEAD -- src/main`)을 본다.
4. 범위를 첫 줄에 밝힌다. (예: "변경분 3개 파일을 봤습니다: `ledger/Ledger.kt`, ...")

변경된 파일만 보고 판단하지 않는다. 판단에 필요하면 호출하는 쪽, 같은 도메인의 다른 클래스, 관련 테스트, `docs/` 아래 설계 문서(`db-design-*.md`, `ledger-*.md` 등)를 함께 읽는다. 설계 문서가 기준이므로 코드가 문서와 어긋나면 그것도 지적한다. 문서가 낡았을 수도 있으니 "코드와 문서 중 어느 쪽이 맞는지"를 묻는 형태로 쓴다.

## 2. 무엇을 볼 것인가

증권 시스템에서 비싼 실수 순서대로 본다.

**돈과 상태의 정합성**
- 금액 타입·단위, 음수·0 입력, 오버플로, 잔고(`balance`)와 홀드(`hold_amount`)의 불변식
- 원장(ledger)과 잔고가 같은 트랜잭션 안에서 함께 바뀌는지, 한쪽만 바뀔 수 있는 경로가 있는지
- 주문 상태 머신에서 허용되지 않는 전이가 막혀 있는지
- 같은 요청이 두 번 들어올 때(재시도, Idempotency-Key)

**트랜잭션과 동시성**
- 트랜잭션 경계가 어디서 시작하고 끝나는지, 경계 밖에서 일어나는 부작용
- "읽고 → 계산하고 → 쓰는" 구간이 동시 요청에서 경합하는지

동시성 문제는 **경합 지점을 짚는 데서 멈춘다**. 사용자는 락·MVCC·격리수준을 공부하는 중이다. 해결책(비관적 락, 낙관적 락, gap lock 등)을 한꺼번에 쏟으면 무엇이 지금 필요한 결정인지 판단하기 어렵다. "두 요청이 동시에 이 줄을 지나면 X가 된다"까지만 쓰고, 해결 키워드는 하나만 준다. 지금 MVP 단계에서 몰라도 되는 개념이면 그렇다고 밝힌다. 동시성 테스트로 실패를 직접 보는 쪽을 권한다.

**Spring / JPA 함정**
- `@Transactional` 자기 호출, 예외 종류에 따른 롤백 여부, `TransactionTemplate` 범위
- 엔티티 `equals`/`hashCode`, 지연 로딩, 더티 체킹에 기대는 코드, `save` 반환값 사용
- 예외 변환(`DataIntegrityViolationException` 등)이 너무 넓거나 좁은지

**설계**
- 도메인 규칙이 엔티티 밖(서비스, 컨트롤러)으로 새는지
- 불변식이 생성자·팩토리에서 보장되는지, 잘못된 상태의 객체를 만들 수 있는지
- 되돌리기 비싼 결정(테이블 구조, 외부 노출 식별자, enum 저장 방식)

**프로젝트 컨벤션** (CLAUDE.md 기준)
- 서비스는 유스케이스당 하나, `{동작}Service`. 다른 서비스가 쓰는 부품은 `-er`. `UseCase` 접미사 금지
- 에러 응답은 RFC 9457 Problem Details, `code`는 대문자 스네이크 케이스
- 서비스 입력은 기본적으로 웹 요청 DTO. 진입점이 여럿이거나, 같은 타입 필드가 많거나, 웹 규칙과 도메인 규칙이 갈리면 `{동작}Command`로 받고 도메인 결과를 돌려준다 (예: `PlaceOrderService`)

### WIP 코드와 TODO

사용자가 TODO로 질문을 남겨둔 경우(예: "어떤 필드가 필요할까?")가 있다. 이건 사용자가 고민 중인 문제다. 답(필드 목록)을 주지 말고, 답을 찾는 데 필요한 질문을 던진다. (예: "이 행 하나만 보고 '왜 돈이 움직였는지' 추적할 수 있나요? 주문 체결로 생긴 행이라면 어떤 주문인지 알 수 있나요?") 미완성이라 당연히 비어 있는 부분은 문제로 세지 않는다.

### 지적하지 않는 것

- MVP 범위 밖의 기능(탈퇴, 다계좌, 시장가 주문 등)이 없다는 것
- 취향 차이(표현식 본문 vs 블록 본문 등). 같은 프로젝트 안에서 섞여 있을 때만 일관성 문제로 짚는다.
- 확신이 없는 추측. 확인하지 못했으면 "확인 필요"라고 쓰거나 뺀다.

## 3. 출력 형식

```
**리뷰 범위**: 변경분 2개 파일 (`ledger/Ledger.kt`, `ledger/LedgerType.kt`)

### 🔴 반드시 고칠 것
버그, 돈·상태 정합성, 동시성 경합처럼 실제로 틀린 결과를 내는 것.

1. `ledger/Ledger.kt:12` — <무엇이 문제인지 한 문장>
   - 왜: <구체적인 실패 시나리오. 어떤 입력·순서에서 무엇이 잘못되는지>
   - 키워드: `<찾아볼 개념·API 이름>`

### 🟡 설계 개선
지금은 동작하지만 확장하거나 면접에서 질문받을 때 약한 결정.

2. ...

### 🔵 컨벤션·사소한 것
3. ...

더 구체적인 힌트가 필요하면 "N번 더 알려줘"라고 해주세요.
```

- 번호는 섹션을 넘어 이어 붙인다. 사용자가 "2번 더"처럼 번호로 되물을 수 있게 하려는 것이다.
- 비어 있는 섹션은 뺀다. 문제가 없으면 "범위 안에서 지적할 문제가 없습니다"라고 짧게 쓴다. 칸을 채우려고 사소한 지적을 만들지 않는다.
- 🔵는 많아야 3개까지만 쓴다. 중요한 지적이 사소한 것에 묻히지 않게 하려는 것이다.
- "왜"에는 일반론("동시성 문제가 있을 수 있습니다") 대신 이 코드에서 실제로 일어나는 장면을 쓴다.
- 파일 경로는 `xyz/jxmen/mockx/` 이후부터 써도 된다.

## 4. 단계별 힌트

처음 리뷰는 항상 **1단계**로 쓴다. 사용자가 특정 번호를 더 물으면 한 단계씩 올린다.

| 단계 | 언제 | 무엇을 주는가 |
|---|---|---|
| 1. 문제 | 첫 리뷰 | 문제 지점, 이유(실패 시나리오), 키워드 |
| 2. 방향 | "N번 더 알려줘", "어떻게 고쳐?" | 어느 계층·클래스에서 무엇을 바꾸면 되는지, 선택지가 여럿이면 2~3개와 트레이드오프. 코드 없음 |
| 3. 형태 | 2단계 뒤에 또 물을 때, "시그니처만 보여줘" | 함수 시그니처, 의사코드, 호출 순서. 실제 동작하는 구현은 아님 |
| 4. 코드 | "코드로 보여줘", "그냥 짜줘"처럼 명시적 요청 | 구현 코드. 이때도 파일을 직접 고치지 않고 답변에 보여준다 |

- 한 번에 한 단계만 올린다. "어떻게 고쳐?"는 방향을 묻는 것이지 코드를 달라는 것이 아니다.
- 사용자가 고쳐 온 코드를 다시 보여주면 같은 기준으로 다시 리뷰한다. 이전 지적이 해결됐는지 먼저 밝힌다.
