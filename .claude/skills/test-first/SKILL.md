# test-first

mockx의 개발 흐름은 **시나리오 합의 → Claude가 실패하는 테스트 작성 → 사용자가 `src/main`을 구현해 통과**다. 어떤 케이스를 테스트할지 고르는 일은 면접 대비 영역이라 사용자가 결정한다. Claude는 목록을 제안하고, 테스트 코드와 실행을 맡는다.

## 절대 하지 않는 것

- `src/main` 아래 파일을 만들거나 고치지 않는다. 테스트를 컴파일하려고 스텁 클래스를 만드는 것도 금지다.
- 사용자가 승인하지 않은 케이스를 테스트에 넣지 않는다. 더 필요해 보이면 제안만 한다.
- 실패한 테스트를 통과시키려고 기대값을 바꾸지 않는다. 기대값이 틀렸다고 판단되면 근거와 함께 사용자에게 묻는다.

## 1. 기준 파악

시나리오를 만들기 전에 다음을 읽는다.

1. 대상 기능의 설계 문서: `docs/db-design-*.md`, 관련 비교 문서. 문서의 정책·입력 규칙·에러 응답 표가 기대값의 기준이다.
2. 관련 `src/main` 코드(있다면): 요청 DTO, 컨트롤러 경로, 예외 클래스, 엔티티 메서드.
3. 같은 도메인의 기존 테스트: 헬퍼와 스타일을 그대로 따르기 위해서다.
   - E2E 예: `src/test/kotlin/xyz/jxmen/mockx/account/DepositE2ETest.kt` (`RestClient` + `exchange`, `ApiResponse`, `shouldBeProblem`, `resetTables`)
   - 컨트롤러 단위 예: `order/OrderControllerTest.kt` (`@WebMvcTest` + mockk 서비스 빈, `verify(exactly = 0)`)
   - 도메인 단위 예: `account/AccountTest.kt`
   - 케이스를 어느 테스트에 둘지는 CLAUDE.md 컨벤션의 테스트 구분을 따른다. 입력 검증·401·경로 변수 형식은 컨트롤러 단위, 정합성·서비스 4xx는 E2E다.

문서에 없는 규칙(예: 금액 상한)이 필요하면 추측하지 말고 사용자에게 묻는다. 묻는 항목은 시나리오 목록의 "결정 필요"에 모은다.

## 2. 시나리오 제안

아래 분류로 목록을 만든다. 대상에 해당하지 않는 분류는 뺀다.

| 분류 | 예 |
|---|---|
| 정상 | 올바른 입력, 반복 호출 시 누적 |
| 경계값 | 최소·최대 허용값, 그 ±1, `Long.MAX_VALUE`, 0 |
| 입력 오류 | 누락, null, 타입 불일치, 소수, 범위 밖 → `400 INVALID_INPUT` |
| 인증·권한 | 헤더 없음, 남의 리소스(IDOR) → 없는 리소스와 같은 응답인지 |
| 정합성 | 잔고·hold·원장이 함께 바뀌는지, 실패 시 아무것도 안 바뀌는지, `SUM(ledger.amount) == balance` |
| 상태 전이 | 주문 상태 머신에서 허용/금지 전이 |
| 중복·재시도 | 같은 Idempotency-Key 재요청, 키는 같고 본문이 다른 경우 |
| 동시성 | N개 요청 동시 실행 후 불변식 유지 |

출력 형식:

```
**대상**: 입금 API (`POST /api/accounts/{id}/deposit`)
**기준 문서**: docs/db-design-member.md 5장, 6장

### 제안 시나리오
1. [정상] 내 계좌에 $10,000 입금 → 200, balance 10,000
2. [경계값] $1, $10,000은 입금된다
3. ...

### 결정 필요
- A. 1회 입금 상한이 문서에 없습니다. 상한을 둘까요? 둔다면 얼마인가요?

### 테스트 종류
- E2E (DepositE2ETest에 추가): 1~7
- 도메인 단위 (AccountTest): 8

넣을 번호를 골라 주세요. 빼거나 바꿀 케이스도 말해 주세요.
```

- 각 시나리오에 기대 결과(상태 코드, `code`, DB 상태)를 한 줄로 붙인다. 사용자가 기대값까지 검토할 수 있어야 한다.
- 시나리오마다 "왜 이 케이스가 필요한지"가 자명하지 않으면 짧게 덧붙인다. (예: "`Long.MIN_VALUE` — 절댓값 비교로 검증하면 오버플로로 통과해 버린다")
- 사용자가 고를 때까지 테스트 코드를 쓰지 않는다.

## 3. 테스트 작성

### 컴파일 문제 먼저 판단

Kotlin은 테스트가 없는 클래스·메서드를 참조하면 **테스트 소스 전체가 컴파일되지 않아** 다른 테스트까지 돌지 않는다.

- **API 기능**이면 E2E로 쓴다. HTTP와 SQL로만 검증하므로 `src/main` 심볼을 참조하지 않아 미구현이어도 컴파일된다.
- **컨트롤러 단위 테스트**는 컨트롤러, 서비스, Command, 결과 타입을 참조하므로 이것들이 있어야 컴파일된다. 없으면 입력 검증 케이스도 일단 E2E로 쓰고, 구현 뒤 컨트롤러 테스트로 옮길지 사용자에게 묻는다.
- **도메인 단위 테스트**가 아직 없는 메서드를 참조해야 하면, 쓰기 전에 사용자에게 필요한 시그니처를 알려준다. (예: "`Account.withdraw(amount: Money)`가 있어야 컴파일됩니다") 사용자가 시그니처를 먼저 만들지, E2E로만 갈지 정하게 한다.

### 작성 규칙

- Kotest `DescribeSpec`, `describe` → `context("~하면")` → `it("~한다")` 구조. 이름은 한국어 문장이다.
- 경계값처럼 입력만 다른 케이스는 `withData`로 묶는다. `withData` 항목에는 `beforeEach`가 돌지 않으므로 항목 안에서 `resetTables()`를 호출한다. (기존 코드의 주석 참고)
- 에러 응답은 RFC 9457 형식을 검증한다: 상태 코드, `application/problem+json`, `status`, `code`(대문자 스네이크), `instance`.
- 실패 케이스는 응답만 보지 말고 **부작용이 없는지**(예수금, hold, 원장 건수)도 확인한다.
- 기대값 숫자는 계산 근거를 주석으로 남긴다. (예: `// 10,000 + 2,500 + 1`)
- 헬퍼가 다른 E2E 테스트와 겹치면 새로 만들지 말고 기존 것을 쓴다. 세 번째로 복붙하게 되면 공통 헬퍼로 빼자고 제안한다.
- 파일 상단 KDoc에 테스트 대상, 기준 문서, 핵심 정책을 적는다.

### 동시성 테스트

- `Executors.newFixedThreadPool` + `CountDownLatch`(출발 신호용, 완료 대기용)로 N개 요청을 동시에 출발시킨다.
- 검증은 **불변식**으로 한다: 최종 잔고 = 초기 잔고 ± 성공 건수 × 금액, 원장 건수 = 성공 건수, 잔고 ≥ 0.
- 성공/실패 건수를 모두 센다. 실패가 예상한 이유(잔고 부족 등)인지 상태 코드로 확인한다.
- 락 없이 구현돼 있으면 이 테스트가 **간헐적으로** 실패할 수 있다고 미리 알린다. 한 번 통과했다고 안전한 게 아니다.

## 4. 실행과 보고

```bash
./gradlew test --tests 'xyz.jxmen.mockx.account.DepositE2ETest'
```

Testcontainers를 쓰므로 Docker가 떠 있어야 한다. Docker 오류로 실패하면 테스트 결과가 아니라 환경 문제라고 따로 보고한다.

실행 후 케이스마다 아래로 분류한다. 결과 XML은 `build/test-results/test/`에 있다.

| 분류 | 의미 | 할 일 |
|---|---|---|
| 🔴 미구현 실패 | 기대대로 실패. 구현하면 통과할 것 | 무엇이 없어서 실패했는지 한 줄 (예: 404 대신 405 — 엔드포인트 없음) |
| 🟡 우연히 통과 | 구현 전인데 통과 | 원인을 찾는다. 테스트가 너무 느슨한지(예: 상태 코드만 보고 DB를 안 봄), 기존 코드가 이미 처리하는지 |
| ⚪ 테스트 오류 | 테스트 자체 버그, 환경 문제 | 고치고 다시 실행. 고친 내용을 보고 |
| ✅ 통과 | 이미 구현된 부분 | 개수만 |

```
**실행**: DepositE2ETest — 12개 중 🔴 9 / 🟡 1 / ✅ 2

🔴 미구현 실패
- `금액이 허용 범위를 벗어나면 > 0이면 ...` — 400 대신 200. 금액 검증 없음
...

🟡 우연히 통과
- `X-Member-Id 헤더가 없으면 ...` — CurrentMember 리졸버가 이미 401을 낸다. 의도한 통과로 보입니다

다음: 🔴 1~3번은 DTO 검증, 4번은 서비스의 소유자 확인에서 해결됩니다.
```

- "다음"에는 어느 계층에서 해결될지 **위치만** 짚는다. 구현 방법은 쓰지 않는다. 사용자가 물으면 `hint-review` 방식(방향 → 시그니처)으로 답한다.
- 합의한 시나리오 목록을 설계 문서의 테스트 섹션(예: `db-design-member.md` 8장)에 반영할지 마지막에 묻는다.
