# resume-task

작업을 이어서 할 때 가장 비싼 건 "어디까지 했고 뭐가 남았는지"를 다시 떠올리는 일이다. 이 스킬은 흩어진 단서를 모아 바로 다음 행동을 고를 수 있게 한다. **읽기만 한다.** 파일을 고치거나, 커밋하거나, 브랜치를 바꾸지 않는다.

## 1. 단서 모으기

아래를 한 번에(병렬로) 확인한다. 없는 항목은 조용히 건너뛴다.

**Git**
```bash
git branch --show-current
git status --short
git log --oneline main..HEAD          # 이 브랜치에서 한 일
git log -1 --format='%h %s (%cr)'     # 마지막 커밋과 경과 시간
git diff HEAD --stat                  # 커밋 안 된 변경 규모
git stash list
```
- `[WIP]` 커밋이 있으면 그 커밋의 변경(`git show --stat <hash>`)을 본다. 무엇이 진행 중인지 가장 직접적인 단서다.
- 커밋 안 된 변경이 있으면 diff를 읽고 무엇을 하다 멈췄는지 한 줄로 요약한다.

**미완성 표시**
```bash
git diff main...HEAD -U0 | grep -nE '^\+.*(TODO|FIXME|XXX)'
git diff HEAD -U0 | grep -nE '^\+.*(TODO|FIXME|XXX)'
```
브랜치 전체가 아니라 **이번 브랜치에서 새로 생긴** TODO만 본다. 오래된 TODO까지 쏟으면 지금 할 일이 묻힌다.

**테스트 상태**
- 테스트는 실행하지 않는다(Testcontainers라 느리다). `build/test-results/test/*.xml`에서 마지막 실행 결과를 읽는다.
  - 실패·에러가 있는 테스트 케이스 이름과 실패 메시지 첫 줄
  - XML 파일 수정 시각과 `src/` 아래 가장 최근 수정 시각을 비교해서, 결과가 그 뒤의 코드 변경을 반영하지 못했으면 "결과가 오래됨"이라고 표시한다.
- 사용자가 원하면 그때 `./gradlew test`를 돌린다.

**문서와 기록**
- `docs/*.md`의 작업 목록·진행 상황 섹션에서 `- [ ]` 미완료 항목 (현재 브랜치와 관련된 도메인 위주)
- `docs/interview-drill-log.md`의 `[미해결]` 항목 (있으면 개수와 최근 것 1~2개)
- 커밋 전 점검 기록: `/tmp/review-diff-<브랜치명>-*.md` (브랜치명의 `/`는 `-`). 있으면 가장 최근 파일의 "손볼 목록"만 가져온다.
- CLAUDE.md의 MVP 범위 대비 어디까지 왔는지

## 2. 요약 출력

한 화면 안에 들어오게 쓴다. 단서를 나열하기보다 **해석**해서 쓴다.

```
## 📍 feature/deposit — 입금 API 진행 중
마지막 커밋: 3bfbb96 [WIP] 입금 API 개발중 (14시간 전)

**한 일** (main 대비 5커밋)
- 원장 엔티티·DB 매핑, 내 정보 조회에 금액 추가
- 입금 API: 컨트롤러·DTO까지 (WIP)

**멈춘 지점**
- 커밋 안 된 변경 없음
- `account/AccountService.kt:23` TODO: 원장 기록 위치 고민 중

**테스트** (마지막 실행: 어제 22:10, 이후 코드 변경 있음 → 결과가 오래됨)
- DepositE2ETest 12개 중 9개 실패 — 금액 검증, 원장 기록 미구현

**남은 일**
- [ ] 입금 서비스 + 원장 기록 (docs/db-design-account.md 4장)
- 커밋 전 점검 손볼 목록 2건 (/tmp/review-diff-feature-deposit-20261022-2310.md)
- 모의면접 미해결 1건: 동시 hold 경합

**다음 할 일 추천**
1. DepositE2ETest의 금액 검증 실패부터 — DTO 검증만으로 4개가 풀림
2. ...
```

- "다음 할 일 추천"은 2~3개, 이유를 붙인다. 실패 테스트가 있으면 그게 가장 구체적인 다음 할 일이다. 범위가 작고 확실한 것부터 둔다.
- 추천에 구현 방법은 쓰지 않는다. 어느 파일·계층의 일인지까지만 쓴다. (백엔드는 사용자가 직접 구현한다)
- 단서끼리 어긋나면 짚는다. (예: "문서 작업 목록엔 완료로 돼 있는데 해당 테스트가 실패 중")
- 확인하지 못한 항목(파일 없음 등)은 출력에서 뺀다. 빈 섹션을 만들지 않는다.
- 사용자가 다음 행동을 고르면 그에 맞는 스킬을 안내한다: 테스트 추가는 `test-first`, 코드 점검은 `hint-review`, 문서 갱신은 `design-note`, 커밋 전 점검은 `review-diff-before-commit`.
