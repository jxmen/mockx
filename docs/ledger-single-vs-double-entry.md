# 단식부기 vs 복식부기

> 최종 수정: 2026-10-22. 원장(ledger) 설계 전에 두 방식의 차이를 정리한 문서다. 계좌 테이블과 입금 흐름은 [`db-design-account.md`](db-design-account.md)를 참고한다.
>
> 예시 금액은 원 단위로 썼지만, mockx의 예수금은 USD다.

## 1. 예시 상황

- 회원 A가 10,000원을 입금한다.
- 회원 A가 회원 B의 주식을 3,000원에 산다.

## 2. 단식부기: 사건 하나에 한 줄

```
 ┌──────────────── 원장 ────────────────┐
 │ 계좌    유형     금액       잔액    │
 ├──────────────────────────────────────┤
 │ A       입금    +10,000    10,000   │  ← 이 돈은 어디서 왔지? (기록 없음)
 │ A       매수     -3,000     7,000   │
 │ B       매도     +3,000     3,000   │  ← 위 줄과 같은 거래인지 알 수 없음
 └──────────────────────────────────────┘
```

- 내 계좌에 무슨 일이 있었는지만 기록한다. 은행 앱의 거래내역과 같다.
- 단순하지만 아래 두 가지를 확인할 수 없다.
  - 돈이 어디서 생겼는지 모른다.
  - A의 -3,000과 B의 +3,000이 같은 거래인지 모르고, 한쪽만 기록돼도 알아챌 수 없다.

## 3. 복식부기: 거래 하나에 두 줄 이상, 합계는 항상 0

```
  거래 #1 (입금)                       거래 #2 (체결)
 ┌───────────────────────────┐       ┌───────────────────────────┐
 │ 회원A 예수금     +10,000  │       │ 회원A 예수금      -3,000  │
 │ ???              -10,000  │       │ 회원B 예수금      +3,000  │
 ├───────────────────────────┤       ├───────────────────────────┤
 │ 합계                   0  │       │ 합계                   0  │
 └───────────────────────────┘       └───────────────────────────┘
```

- 돈은 어딘가에서 와서 어딘가로 간다. 그래서 모든 거래에 출발지와 도착지를 함께 기록한다.
- 거래마다 합계가 0이므로 **전체 원장의 합계도 항상 0**이어야 한다. 0이 아니면 어딘가에 버그나 누락이 있다는 뜻이다. 이것이 복식부기의 핵심 가치다.
- 실제 회계에서는 `+`/`-` 대신 차변(debit)/대변(credit)이라는 용어를 쓴다. 개념을 잡을 때는 부호로 생각해도 충분하다.

## 4. 가상 머니 입금을 복식부기로 기록하는 방법

위 그림의 `???`, 즉 돈의 출발지가 문제다.

- 실제 은행 입금이라면 "회사가 보유한 은행 예금"이 상대 계정이 된다.
- 가상 머니는 외부에서 들어오는 돈이 없으므로, **돈을 발행하는 시스템 계정**을 하나 만든다.

```
  거래 #1: 회원 A에게 가상 머니 10,000 지급
 ┌──────────────────────────────────────┐
 │ 회원A 예수금           +10,000       │
 │ [시스템] 가상머니 발행  -10,000       │
 ├──────────────────────────────────────┤
 │ 합계                         0       │
 └──────────────────────────────────────┘

  여러 명이 입금한 뒤 잔액
 ┌──────────────────────────────────────┐
 │ 회원A 예수금            7,000        │
 │ 회원B 예수금           53,000        │
 │ [시스템] 가상머니 발행  -60,000  ◀── 지금까지 발행한 총액(음수)
 ├──────────────────────────────────────┤
 │ 합계                        0        │
 └──────────────────────────────────────┘
```

- 발행 계정의 잔액은 계속 음수로 쌓인다. 그 절댓값이 지금까지 시스템이 찍어낸 가상 머니 총액이다.
- 수수료를 도입하면 `[시스템] 수수료 수익` 계정을 추가한다. 예를 들어 체결 거래에 `회원A -15 / 수수료수익 +15` 줄이 붙는다.

## 5. 복식부기를 도입하면 생기는 설계 문제

1. **시스템 계정을 어디에 둘 것인가**
   - 현재 `account` 테이블은 `member_id`가 `NOT NULL` + UNIQUE이고, `number`는 증권 계좌번호다. "가상머니 발행" 같은 계정이 들어갈 자리가 없다.
   - 선택지 A: `account`에 시스템 계정 행을 넣는다. 그러려면 제약을 바꿔야 한다.
   - 선택지 B: 원장용 계정을 증권 계좌와 분리한다. 증권 계좌 하나가 원장 계정 하나에 대응된다.
2. **거래와 분개(entry)를 나눌 것인가**
   - "이 줄들이 한 거래다"를 묶으려면 보통 `거래 1 : N 분개` 구조를 쓴다.
3. **작업량**
   - 단식부기라면 원장에 `amount`, `balance_after` 정도만 추가하면 끝난다.
   - 복식부기는 위 두 가지가 추가 작업이다.

## 6. 비교 요약

| 항목 | 단식부기 | 복식부기 |
|---|---|---|
| 기록 단위 | 계좌별 사건 1줄 | 거래 1건 = 분개 2줄 이상 |
| 돈의 출처 | 알 수 없음 | 상대 계정으로 항상 기록 |
| 정합성 검증 | 계좌별 `SUM(amount) == balance` | 계좌별 검증 + 전체 합계 = 0 |
| 한쪽만 기록되는 누락 | 알아채기 어려움 | 합계가 0이 아니므로 바로 드러남 |
| 테이블 구조 | 원장 테이블 1개 | 거래 + 분개, 시스템 계정 필요 |
| 구현 비용 | 낮음 | 높음 |

## 7. mockx의 선택

- MVP는 **단식부기**로 시작한다. 1~2주 범위에서는 복식부기 구조의 추가 비용이 크다.
- 다만 매수/매도 원장에 **체결 ID**를 남긴다. 그러면 "A의 -3,000과 B의 +3,000이 같은 체결"이라는 연결은 확인할 수 있다. 복식부기의 장점 일부를 적은 비용으로 가져가는 방법이다.
- 복식부기 전환은 MVP 이후 확장 후보로 남긴다.

## 8. 면접 꼬리 질문 대비

- **왜 복식부기로 하지 않았나?** MVP 범위에서 시스템 계정과 거래/분개 구조를 추가하는 비용이 크다고 판단했다. 대신 체결 ID로 거래 양쪽을 연결해 추적할 수 있게 했다.
- **복식부기의 장점은?** 모든 돈의 이동에 출처와 목적지가 남는다. 전체 합계가 0이라는 불변식 하나로 누락이나 버그를 검증할 수 있다.
- **가상 머니의 출처는 어떻게 기록하나?** 발행용 시스템 계정을 상대 계정으로 둔다. 그 계정 잔액의 절댓값이 총 발행액이 된다.

## 9. 현재 테이블 (`V2__create_ledger.sql`)

### ledger

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | `BIGINT` | PK, auto increment |
| `account_id` | `BIGINT` | NOT NULL, `idx_ledger_account_id` |
| `amount` | `BIGINT` | NOT NULL (변동 금액, 달러) |
| `balance_after` | `BIGINT` | NOT NULL (변동 후 예수금) |
| `type` | `VARCHAR(20)` | NOT NULL (`LedgerType` enum 이름. 현재 `DEPOSIT`만 있음) |
| `created_at` | `DATETIME(6)` | NOT NULL |
| `updated_at` | `DATETIME(6)` | NOT NULL |

- 단식부기라 계좌 한 줄짜리 기록이다. 상대 계정이 없다.
- `balance_after`를 남겨서 "예수금 = 원장 금액 합계 = 마지막 `balance_after`"를 검증할 수 있다(`DepositE2ETest`).
- 체결 ID 컬럼과 매수·매도 타입은 아직 없다. 체결 작업 때 추가한다(7장).
