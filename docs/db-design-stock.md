# 종목(Stock) 설계

> 최종 수정: 2026-10-24. 테이블 공통 규칙(단수형 이름, `DATETIME(6)` UTC, 제약 이름, Flyway)은 [`db-design-member.md`](db-design-member.md)를 참고한다.

## 1. 정책

| 항목 | 결정 |
|---|---|
| 시장 | 미국 상장 종목(NASDAQ, NYSE Arca)을 다룬다. 거래소는 저장하지 않고 mockx 안에서 똑같이 매칭한다. 한국 종목코드(`005930` 같은 6자리 숫자)는 고려하지 않는다 |
| 식별자 | 내부는 `id`, 외부(API)는 티커(`MU`, `AAPL`)로 노출한다 |
| 저장하는 정보 | 종목 마스터(정적 정보) 중 주문 접수에 필요한 최소한만 둔다. 가격은 저장하지 않는다 |
| 통화 | USD. 예수금도 달러 단위다 ([`db-design-account.md`](db-design-account.md) 1장). 금액은 정수 센트로 저장한다(4.1) |

## 2. 종목 마스터와 시세

증권 시스템은 종목 데이터를 두 갈래로 나눈다.

| 구분 | 예시 | 바뀌는 빈도 | 누가 바꾸나 |
|---|---|---|---|
| 종목 마스터 (정적) | 티커, 종목명, 거래정지 여부 | 거의 안 바뀜 | 관리자, 마이그레이션 |
| 시세 (동적) | 현재가, 등락률, 거래량, 호가 | 체결될 때마다 | 체결 결과 |

- 현재가는 마지막 체결가다. 매칭 엔진이 만드는 값이라 종목 마스터에 두지 않는다.
- 지정가 주문의 가격은 사용자가 정한다. 그래서 주문 접수 단계에는 현재가가 필요 없고, "그 종목이 존재하는가"만 확인하면 된다.

### 가격 컬럼을 지금 두지 않는 이유

| 선택지 | 컬럼 | 장점 | 단점 |
|---|---|---|---|
| **A. 최소 (선택)** | `id`, `symbol`, `name` | 다음 작업(주문 접수)에 필요한 만큼만 만든다 | 기준가가 필요해지면 마이그레이션을 하나 더 추가한다 |
| B. 기준가 포함 | A + `base_price` | 첫 체결 전 가격 문제가 미리 정리된다 | 당장 쓰는 곳이 없는 컬럼이 생긴다 |

- 이유: 다음 작업인 주문 접수(예수금 hold까지)는 종목 존재 여부만 쓴다. 최소 정보로 도메인을 만들고 넘어간다.
- 포기한 것: 첫 체결 전에 보여줄 가격이 없다. 화면과 봇에 기준 가격이 필요해지는 시점에 추가한다(5장).

## 3. 테이블

### stock

| 컬럼 | 타입 | 제약 |
|---|---|---|
| `id` | `BIGINT` | PK, auto increment (내부 식별자) |
| `symbol` | `VARCHAR(10)` | NOT NULL, `uk_stock_symbol` (외부 노출 식별자) |
| `name` | `VARCHAR(100)` | NOT NULL (종목명. 예: `Micron Technology`) |
| `created_at` | `DATETIME(6)` | NOT NULL |
| `updated_at` | `DATETIME(6)` | NOT NULL |

- 컬럼·필드 이름은 `symbol`로 한다. 티커 심볼(ticker symbol)을 줄인 이름이고, 본문의 "티커"는 이 값을 가리킨다.
- 미국 티커는 보통 영문 대문자 1~5자다. 여유를 두고 `VARCHAR(10)`으로 한다.
- 티커를 PK로 쓰지 않는 이유는 티커가 바뀔 수 있어서다. (예: 2022년 Facebook의 티커가 `FB`에서 `META`로 바뀌었다) `id`를 FK로 쓰면 티커가 바뀌어도 주문 테이블은 그대로 둘 수 있다. `account`의 `id` + `number` 구성과 같은 이유다.
- 상장폐지된 티커가 다른 회사에 다시 배정되는 경우는 아직 다루지 않는다. `uk_stock_symbol`과 충돌하므로 4장에서 정한다.
- `created_at`, `updated_at`은 다른 엔티티와 같이 `BaseTimeEntity`(JPA Auditing)가 채운다. 엔티티가 `BaseTimeEntity`를 상속하지 않으면 INSERT 때 NOT NULL 위반이 난다.
- Flyway로 종목 데이터를 넣으면 Auditing이 동작하지 않는다. INSERT 문에 시각을 직접 넣어야 한다. DB `DEFAULT`를 쓰지 않는 규칙([`db-design-member.md`](db-design-member.md) 2장)은 그대로 지킨다. `CURRENT_TIMESTAMP`는 세션 `time_zone`을 따르므로, UTC 리터럴이나 `UTC_TIMESTAMP(6)`을 쓴다.

## 4. 결정

### 4.1 주문 가격·금액 단위

예수금(`Money`)은 정수 달러다. 미국 주가는 센트 단위라서(예: $187.43) 지금 단위로는 주문 금액을 표현할 수 없다.

```
MU 지정가 $187.43 × 10주 = $1,874.30 hold
  → Money(Long 달러)로는 $1,874 또는 $1,875. hold/release 합계가 원장과 센트 단위로 어긋난다
```

| 선택지 | 저장 | 장점 | 단점 |
|---|---|---|---|
| A. 정수 센트 | `BIGINT` (187.43 → `18743`) | 지금 `Long` 기반 `Money`와 계산 방식이 같다. 반올림 문제가 없다 | 기존 `balance`, `hold_amount`, `ledger` 데이터를 ×100 하는 마이그레이션, 입금 API 단위 변경(프론트 포함)이 필요하다 |
| B. `BigDecimal` | `DECIMAL(p, s)` | 소수 그대로 표현한다. 단위 변환이 없다 | `Money` 타입과 컬럼 타입을 바꿔야 한다. 연산마다 scale과 반올림 모드를 정해야 한다 |
| C. 정수 달러 유지 | `BIGINT` | 바꿀 것이 없다 | 주문 가격을 $1 단위로 제한해야 한다. 실제 시장(호가 $0.01)과 다르다 |

- 결정: A — `Money`의 `Long` 연산과 테스트를 그대로 살릴 수 있고, 데이터가 아직 적어서 마이그레이션 비용이 작다. 단위를 바꾸려면 데이터가 쌓이기 전인 지금이 가장 싸다. 기존 데이터는 V3 마이그레이션(`V3__convert_money_to_cents.sql`)으로 ×100 한다.
- 결정: API도 정수 센트로 주고받는다. DB·`Money`와 단위가 같아 서버에는 변환이 없고, 달러 표시·입력 변환은 프론트가 맡는다. JSON 숫자 소수는 클라이언트가 부동소수로 읽어 오차가 생길 수 있어서 쓰지 않는다.

### 4.2 티커 재사용

상장폐지된 티커는 나중에 다른 회사에 배정될 수 있다. 주문 이력 때문에 과거 행을 지울 수 없으면, 같은 티커로 새 종목을 넣을 때 `uk_stock_symbol`과 충돌한다.

| 선택지 | 내용 |
|---|---|
| A. MVP에서 다루지 않음 | 상장폐지·재배정을 하지 않는다. `uk_stock_symbol`을 그대로 두고 6장 한계에 기록한다 |
| B. 상장 상태 + 활성 티커만 유니크 | 상태 컬럼을 두고 상장 중인 행만 유니크하게 한다. MySQL에는 부분 인덱스가 없어서, 상장 중일 때만 티커 값을 갖고 폐지되면 `NULL`이 되는 생성 컬럼에 UNIQUE를 거는 식으로 우회한다 (확인 필요) |

- 결정: A — mockx는 종목을 Flyway로 고정해서 넣고 상장폐지 기능이 없다. B는 거래정지·상장 상태를 다룰 때(5장) 함께 검토한다.

### 4.3 티커 대소문자

MySQL 기본 콜레이션(`utf8mb4_0900_ai_ci`)은 대소문자를 구분하지 않는다. `mu`로 조회해도 `MU`가 나온다. 반면 인메모리 매칭 엔진의 종목별 오더북을 `Map<String, OrderBook>`으로 두고 요청 문자열을 그대로 키로 쓰면 `mu`와 `MU`가 다른 오더북이 된다. `username`에서 같은 주의를 적어 두었다([`db-design-member.md`](db-design-member.md) 3장).

| 선택지 | 내용 |
|---|---|
| A. API 경계에서 대문자로 정규화 | 요청 티커를 대문자로 바꾼 뒤 조회한다. 저장 데이터도 대문자만 넣는다 |
| B. 대문자만 허용 | 소문자가 오면 400으로 거절한다 |
| C. 오더북 키를 `stock.id`로 | 티커는 조회에만 쓰고, 매칭 엔진은 내부 `id`로 오더북을 찾는다 |

- 결정: C + A — 매칭 엔진은 티커 변경과도 무관한 `id`를 키로 쓰고, 조회 결과가 DB 콜레이션에 기대지 않도록 입력을 정규화한다.
- 규칙: 심볼은 대문자만 쓴다. 백엔드 응답과 프론트 요청 모두 대문자다(`MU`). 백엔드는 요청 심볼을 대문자로 바꾼 뒤 조회한다.
- DB 콜레이션: `symbol`은 기본 콜레이션(`utf8mb4_0900_ai_ci`) 그대로 둔다. 대소문자를 구분하지 않으므로, 정규화를 빠뜨려도 `mu`가 별개 종목으로 저장되지 않고 `uk_stock_symbol`에 막힌다. 콜레이션은 정규화를 대신하지 않는 두 번째 방어선이다.

### 4.4 종목 데이터를 어떻게 넣는가

- 결정: Flyway 마이그레이션(`V4__create_stock.sql`)으로 몇 종목을 미리 넣는다. 종목 등록 API는 MVP에 필요 없다.

| 심볼 | 종목명 | 상장 거래소 |
|---|---|---|
| `SPY` | SPDR S&P 500 ETF Trust | NYSE Arca |
| `QQQM` | Invesco NASDAQ 100 ETF | NASDAQ |
| `QLD` | ProShares Ultra QQQ | NYSE Arca |
| `TQQQ` | ProShares UltraPro QQQ | NASDAQ |
| `SOXL` | Direxion Daily Semiconductor Bull 3X Shares | NYSE Arca |
| `SGOV` | iShares 0-3 Month Treasury Bond ETF | NYSE Arca |
| `MU` | Micron Technology | NASDAQ |
| `SKHY` | SK hynix ADR (원주는 한국거래소 `000660`) | NASDAQ |

- 결정: `SPY`, `QLD`, `SOXL`, `SGOV`는 NYSE Arca 상장이다. 1장 정책을 "미국 상장 종목(NASDAQ, NYSE Arca)"으로 넓혀 그대로 넣는다.
- 결정: 종목 목록 API(4.5)와 상세 조회 API를 이번 단계에서 만든다. 상세 조회 스펙은 4.6에 정리했다.

### 4.5 종목 목록 API

`GET /api/stocks`

```json
{
  "stocks": [
    { "symbol": "SPY", "name": "SPDR S&P 500 ETF Trust" },
    { "symbol": "QQQM", "name": "Invesco NASDAQ 100 ETF" }
  ]
}
```

| 항목 | 결정 |
|---|---|
| 응답 형태 | 최상위 배열이 아니라 `stocks` 필드로 감싼다. 나중에 페이지 정보 같은 필드를 붙여도 기존 클라이언트가 깨지지 않는다 |
| 노출 필드 | `symbol`, `name`. 내부 `id`와 생성·수정 시각은 노출하지 않는다(1장) |
| 인증 | 필요 없음. 종목 마스터는 로그인 전에도 보는 공개 정보다. `X-Member-Id` 없이 200 |
| 정렬 | 기본은 `id` 오름차순(넣은 순서). `sort` 파라미터로 바꿀 수 있다(아래) |
| 페이지네이션 | 없음(5장) |

정렬 파라미터 규칙:

| 항목 | 결정 |
|---|---|
| 형식 | Spring 관례 `sort=필드[,asc\|desc]`. 방향을 생략하면 오름차순, 방향은 대소문자를 구분하지 않는다(`DESC` 허용) |
| 허용 필드 | `id`, `symbol`만. 허용 목록 밖의 필드(`createdAt`처럼 엔티티에 있는 필드, `name`처럼 응답에 있는 필드 포함)는 거절한다 |
| 정렬 기준 개수 | 하나만. `sort=symbol&sort=id,desc`처럼 여러 개면 거절한다 |
| 잘못된 값 | 허용하지 않은 필드, 없는 필드, 잘못된 방향, 여러 개 → `400 INVALID_INPUT`. 무시하고 기본 정렬로 돌려주지 않는다(클라이언트가 오타를 알 수 없다) |

- 허용 목록을 두는 이유: 요청 값을 Spring Data `Sort`로 그대로 넘기면 응답에 없는 내부 필드로도 정렬할 수 있다. 없는 필드는 `PropertyReferenceException`이 나는데, 처리하지 않으면 500이 된다.

### 4.6 종목 상세 API

`GET /api/stocks/{symbol}`

```json
{ "symbol": "MU", "name": "Micron Technology" }
```

| 항목 | 결정 |
|---|---|
| 응답 형태 | 단일 리소스라 감싸지 않는다. 노출 필드는 목록과 같은 `symbol`, `name` |
| 인증 | 필요 없음. 목록 API와 같다(4.5) |
| 대소문자 | 대문자로 바꿔 조회한다(4.3). `mu`, `Mu`로 요청해도 200이고, 응답 `symbol`은 `MU` |
| 형식 검사 | 영문 1~10자만 허용한다. 숫자·특수문자·공백·영문 외 문자, 11자 이상 → `400 INVALID_INPUT` |
| 없는 종목 | 형식은 맞지만 없으면 `404 STOCK_NOT_FOUND` |

형식 검사를 두는 이유:

- 콜레이션 `utf8mb4_0900_ai_ci`의 `ai`는 악센트도 무시한다. 검사 없이 조회하면 `mü`가 `MU`와 같다고 판단되어 200이 나간다. 대문자로 바꿔도 `MÜ`라 막히지 않는다.
- 형식 오류(400)와 없는 종목(404)을 나누면 클라이언트가 오타와 미상장 종목을 구분할 수 있다.
- 길이 상한 10자는 `symbol` 컬럼(`VARCHAR(10)`)에 맞췄다. 11자 이상은 존재할 수 없는 심볼이다.

형식 검사는 대문자로 바꾸기 **전** 원래 입력에 한다. 유니코드 대문자 변환은 영문이 아닌 문자를 영문으로 바꿀 수 있다. 예를 들어 long s(`ſ`, U+017F)는 대문자로 `S`가 되므로, 바꾼 뒤에 검사하면 `ſpy`가 `SPY`로 검사를 통과한다.

- 포기한 것: 실제 미국 티커에는 `BRK.B`, `BF-B`처럼 점·하이픈이 들어간 클래스 주식이 있다. 지금 종목 데이터에는 없으므로 허용하지 않고, 그런 종목을 넣을 때 형식 규칙을 넓힌다.

## 5. 나중으로 미룬 것

| 항목 | 시점 | 비고 |
|---|---|---|
| 기준가(`base_price`) | 봇 유동성 공급 또는 시세 화면 작업 시 | 첫 체결 전 표시 가격, 봇 호가의 기준 |
| 현재가·시세 | 매칭 엔진 작업 시 | 마지막 체결가. 종목 테이블에 둘지 별도로 둘지 그때 정한다 |
| 거래정지 상태 | "거래정지 종목은 주문 거절" 규칙이 필요할 때 | |
| 거래소 구분 (NASDAQ, NYSE Arca 등) | 거래소별로 다르게 처리할 규칙이 생길 때 | 지금은 어느 거래소 종목이든 똑같이 다룬다 |
| 호가 단위 | 주문 가격 검증 작업 시 | 미국 시장은 $1 이상 종목의 호가를 $0.01 단위로 낸다 |
| 종목 목록 페이지네이션 | 종목이 수십 개를 넘을 때 | 지금은 8개라 전부 돌려준다 |
| 종목 아이콘(로고) | 프론트 종목 화면 작업 시 | 프론트 정적 파일을 심볼로 찾는다(`{심볼}.png`, 예: `MU.png`). DB에는 이미지도 URL도 두지 않는다. 관리자가 로고를 바꿔야 하면 오브젝트 스토리지·CDN URL 컬럼(`logo_url`)을 검토한다 |

- 미국 시장에는 한국식 일일 가격제한폭(±30%)이 없다. 대신 급등락 시 거래를 잠시 멈추는 장치(LULD)가 있다. mockx는 다루지 않는다.

## 8. 면접 꼬리 질문 대비

**종목 테이블에 현재가가 없는데요?** 현재가는 마지막 체결가라 매칭 엔진이 만드는 시세 데이터다. 바뀌지 않는 종목 마스터와 체결마다 바뀌는 시세를 분리했다. 주문 접수에는 가격이 필요 없어서 시세는 매칭 엔진 단계로 미뤘다.

**티커를 PK로 쓰면 조인 없이 주문만 보고도 종목을 알 수 있는데, 왜 id를 따로 뒀나요?** 티커는 바뀔 수 있다(`FB` → `META`). 자연키를 FK로 쓰면 티커가 바뀔 때 참조하는 모든 행을 고쳐야 한다. 대리키로 참조하고 티커는 UNIQUE로만 보장한다.

**첫 체결 전에는 가격이 없는데, 사용자는 얼마에 주문을 내나요?** 지정가 주문이라 사용자가 가격을 정한다. 다만 화면에 참고 가격이 없고, 봇도 어디에 호가를 낼지 기준이 없다. 그 단계에서 기준가를 추가한다. 실제 시장도 신규 상장 종목은 공모가를 기준으로 첫 가격을 정한다.

**`toUpperCase()`로 바꾸면 끝 아닌가요? 왜 형식 검사를 따로 하나요?** 두 가지 함정이 있다. 하나는 DB 콜레이션이 악센트까지 무시해서 `mü`가 `MU`로 조회된다는 점이고, 다른 하나는 유니코드 대문자 변환이 영문이 아닌 문자를 영문으로 바꾼다는 점이다(`ſ` → `S`). 그래서 원래 입력을 영문 1~10자로 검사한 뒤에 대문자로 바꾼다. 또 Java `toUpperCase()`는 인자가 없으면 JVM 기본 로케일을 따라서 터키어 로케일에서는 `i`가 `İ`가 된다. 로케일에 영향받지 않는 변환(Kotlin `uppercase()`, Java `toUpperCase(Locale.ROOT)`)을 쓴다.

**소문자 요청 테스트가 정규화 없이도 통과한다면 그 테스트는 의미가 있나요?** E2E 테스트는 "소문자로 요청해도 200"이라는 API 계약을 보장할 뿐, 정규화 코드가 있는지는 확인하지 못한다. 콜레이션이 대신 맞춰 주기 때문이다. 정규화가 실제로 중요한 곳은 DB를 거치지 않는 인메모리 매칭 엔진인데, 그쪽은 오더북 키를 `stock.id`로 정해서(4.3) 문자열 대소문자와 무관하게 만들었다.
